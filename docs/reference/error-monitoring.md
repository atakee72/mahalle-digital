## Error Monitoring (Sentry)
- **Errors only** — `@sentry/astro`, `tracesSampleRate: 0` in both configs; replay sample rates `0` in the client config (replay is browser-only) (5k errors/mo free-tier cap is the whole budget; `sendDefaultPii: false` for GDPR, EU-region org). With `SENTRY_DSN`/`PUBLIC_SENTRY_DSN` unset, init is a documented no-op.
- **Client `beforeSend` noise filter (2026-09-20):** `sentry.client.config.ts` drops what `isClientNoise()` (`src/lib/sentry/clientNoise.ts`, pure, tested with the exact strings from the board) recognises — cancelled view transitions (`AbortError`; `InvalidStateError` ONLY when the text is about transitions / a hidden document), React's „This root received an early update, before anything was able hydrate" fallback notice, and `null (reading 'body')` ONLY when a stack frame is one of Astro's router chunks — `ClientRouter.astro_…js` or the transition module `router.<hash>.js` (a page open during a deploy; the second chunk name reached the board on 2026-10-14 because the filter knew only the first; from our own files the same message is a real bug). They reopened issues after every deploy and every backgrounded tab. Keep it that narrow — never add a pattern for something a member could actually see.
- **`beforeSend` transient filter** (server config): drops OpenAI 429/rate-limit noise, `AbortError`, and transient `MongoNetworkError` timeouts before they ship — the moderation pipeline's per-submission OpenAI calls would otherwise let a provider incident burn the monthly cap. **Also drops `event.environment === 'development'` (2026-09-03, `9c6434f8`)**: the server-side `SENTRY_DSN` stays active in local dev on purpose (diagnostics), but its events — including unhandled promise rejections from throwaway git-worktree dev servers (e.g. Astro's route-manifest reader ENOENT-ing on files a `git reset` removed mid-run) — were landing on the prod board and burning the cap (was the #1 issue, 62 events, before the filter). `development` is dropped, not "non-production", so **preview + production still report** — preview is where the silent-degradation tripwires legitimately fire. This is the server-side twin of the client-side `PUBLIC_SENTRY_DSN`-commented-out fix.
- **Silent-degradation alerts** (Aug 2026, after the OpenAI-credits-exhausted incident starved the newsboard for 4 days with zero errors anywhere): code paths that swallow provider failures and degrade gracefully must emit `Sentry.captureMessage` + `await Sentry.flush(2000)` at the capture site (success responses aren't flushed by middleware — Vercel's freeze eats unflushed events). Implemented in `fetch-daily.ts` (scoring `degraded` flag) and `moderation.ts` `createFailSafeResult` (STATIC message, variable reason in `extra` — else every error string becomes its own issue). `captureMessage` bypasses the beforeSend filter (it only inspects `event.exception`). Alert rule "New issue in production" also fires on resolved→unresolved regression — resolve outage issues after fixing so the next outage re-alerts.
- **Sentry's blind spot: callers OUTSIDE the app.** Anything that reaches the app over HTTP from elsewhere (GitHub-Actions crons, webhooks, uptime probes) can fail entirely without producing a single Sentry event — the request dies at the edge and no app code runs. The Aug 2026 domain cutover killed the air logger this way for 2 days (see `schillerkiez_air_log` above); the only signal was a red Actions tab nobody was watching. **After ANY change to origins, domains, redirects, or auth headers, re-verify every external caller by hand** (`gh run list --workflow=<name>`), and prefer asserting on freshness of the DATA (e.g. `readings: 0` today) over trusting the absence of errors. The general remedy is a **data-freshness watchdog hosted on a schedule the same change can't break** — `checkAirLoggerFreshness()` in `src/lib/kiez/airFreshness.ts`, called from the Vercel-native news cron, is the worked example; copy the shape for any future externally-triggered job. **The second blind spot is a wrong STATUS CODE on our own routes (2026-10-31):** a middleware 404 swallowed every own `/api/auth/*` route for three days (root cause under „Authentication Flow") and nothing fired — no exception, no write, no ping. Two sensors since `c413646f`: (1) `scripts/smoke-auth.mjs` (plain Node, no deps) sends fifteen fixed requests — every own `/api/auth/*` route with an empty body, the two Auth.js reads, landing + login page, the member-API gate `/api/topics` → 401, an unknown auth action → 404 — and `.github/workflows/smoke-auth.yml` runs it against prod every 30 min (GitHub jitter: minutes, sometimes hours), retries once after 60 s, then posts the failing lines to the admin's Telegram (repo secrets `TELEGRAM_BOT_TOKEN` + `TELEGRAM_ADMIN_CHAT_ID`, same values as Vercel; repeats every failing run until fixed). The probe writes nothing (validation precedes every rate-limit charge). A test (`src/lib/smoke/authSmoke.test.ts`) fails when a file in `src/pages/api/auth/` has no row. (2) The four auth forms call `reportUnexpectedAuth()` (`src/lib/sentry/reportUnexpectedAuth.ts`, rule in the pure `src/lib/auth/unexpectedResponse.ts`) when the server answers 404, 5xx, non-JSON, an odd status or the request fails while online — ONE static Sentry message `auth form: unexpected server response` (tags.route, extra.status), so the „new issue" → Telegram bridge pings once; the normal 400/401/403/409/429 vocabulary is never reported; resolve the issue after each incident so a regression re-alerts. **Rule: after any change to `middleware.ts` or `src/pages/api/auth/`, run `node scripts/smoke-auth.mjs http://127.0.0.1:4655` against the local prod build before pushing.** Alert path PROVEN 2026-10-31 03:12: the dispatch against the old `*.vercel.app` host (every check 308) went red after the retry and the bot API answered 200; the prod run was 15/15 green; secrets set from `.env` via `gh secret set` (`gh workflow run smoke-auth.yml -f origin=<wrong host>` repeats the test). **Login stops on auth-astro's own navigation:** with `redirect:false` its `signIn()` still sets `window.location.href` on success and resolves `undefined` (a Response only for a refused login), so `AuthLoginInner` returns right there — the session/login-status fetches that followed were rejected by Safari mid-navigation and the sensor reported a HEALTHY login (Opus review; reproduced + fixed with `scratchpad/auth-sensor/login-race.cjs`). **Both Sentry configs scrub URLs since the same night** (`src/lib/sentry/scrubUrl.ts`, tested): `event.request` loses query string, `query_string` and the Referer header, breadcrumbs lose the query in `url`/`from`/`to` and the Node SDK's `http.query`/`http.fragment` — four pages carry single-use tokens in their query (`/reset-password`, `/verify-email`, `/confirm-email-change`, `/widerrufen`), `/login` the redirect target; a sensor report from the reset page would otherwise have handed anyone with Sentry access a still-valid reset token (security hook + review).
- **Widget**: `AdmErrorsCard.svelte` on `/admin/moderation` (desktop only, between the stat row and title block) via the `requireAdminSession`-gated proxy `GET /api/admin/errors`. Full architecture in `src/components/admin/CLAUDE.md`.
- **Server request-error capture lives in `src/middleware.ts`, NOT the SDK's auto-middleware** (live-debugged 2026-07-19, two real Vercel-serverless failure modes): (1) Astro bundles `sentry.server.config`'s `Sentry.init()` into PAGE chunks only — a cold instance serving only `/api/*` ran with an uninitialized SDK, so the middleware does a side-effect `import '../sentry.server.config'`; (2) Vercel freezes the function the moment the response leaves, eating the SDK's async event POST — the middleware catch does `captureException` + `await Sentry.flush(2000)` + rethrow INSIDE the request window. The SDK's own request handler is disabled (`autoInstrumentation.requestHandler: false` in astro.config.mjs) so this is the single capture point. Don't "simplify" either piece away — each reverts to silently-lost server errors.
