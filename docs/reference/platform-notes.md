### Cold starts are the CPU bill, not traffic (2026-10-13)
Vercel's mail „75 % of the free 4 h Fluid Active CPU" arrived on day 11 of the cycle (the cycle runs from the 14th; the usage page is `vercel.com/<team>/~/usage`, the per-route view is Pro-only). Measured on the local production build (`scratchpad/coldstart/`: `cpu-server.mjs` wraps `dist/server/entry.mjs` and serves `process.cpuUsage()` on :4656, `cpu-probe.cjs` logs in and measures CPU per route, `esmcount.mjs` counts the modules a first request loads, `agg.py` aggregates a `--cpu-prof` by package): a WARM request costs 5–40 ms of CPU, but the FIRST request on a fresh instance cost 1.2–2.9 s — ~1 000 small files resolved and compiled (`@sentry/*` + `@opentelemetry/*` ≈ 650, `date-fns` 304 via its barrel, `jose` + `@auth/core` ≈ 110). With ~2 000 requests a day that is a few hundred cold starts × ~1.5 s ≈ the 5–8 CPU-minutes the chart showed. Fix: `vite.ssr.noExternal` for those packages in `astro.config.mjs` (they are bundled into the server chunks; the first request loads ~60 files): landing 2.9 s → 0.43 s, `/api/kiez-stats` 1.2 s → 0.38 s, login 1.4 s → 0.38 s, warm requests about halved too. Sentry delivery after bundling was proven against a local sink (`sentry-sink.mjs` + a build with `SENTRY_DSN=http://abc@127.0.0.1:4700/1` and a dead `MONGODB_URI` — both are INLINED at build time by Vite, so they cannot be overridden at run time with `--env-file`; rebuild to test). Stays external: `mongodb`/`bson` (130 files, optional native deps), `bcrypt`, `import-in-the-middle` (Sentry's ESM hook). A production instance stays warm for at least 3.5 min between requests (probe 2026-10-13: TTFB 0.1 s after 45/90/150/210 s idle), so UptimeRobot's 5-min ping neither keeps it warm nor matters much. Before adding a package that ships hundreds of files, re-measure; if the chart climbs past ~8 min/day again, the next levers are a warm-keeping ping under the idle timeout or Pro. **Verified 2026-10-19 on the usage page:** 4–10 min/day before the fix, ~2 min/day after (15 min in the week of 10-13…10-19, the Kiez-Brief Sunday 2.3) ⇒ ~1 h of the 4 h per month — closed. Reading that page: its range picker offers only ROLLING windows („Last 7/14/30 Days", typed ranges), no billing-period preset, so the headline „2h 52m / 4h" under „Last 30 Days" summed the pre-fix days too and looked alarming; pick „Last 7 Days" for the current pace, and the reset date lives under Settings → Billing. The usage API refuses the CLI token (`/v1/usage` → 403), so the page is the owner's. **The `noExternal` list is BUILD-ONLY since 2026-11-02 (`aa2d9b65`):** in `astro dev` the same list broke every page from 10-13 to 11-02 with `require is not defined` — `@sentry/astro`'s server entry also exports the build-time integration, which imports `@sentry/vite-plugin` → `@sentry/bundler-plugin-core` → `@sentry/cli` (CommonJS), and Vite's dev runner inlines it as ESM; Rollup converts CommonJS in the build, so prod never saw it, and nobody ran `pnpm dev` for three weeks (found by the ui-polish peer). `astro.config.mjs` gates the list on `process.argv.includes('build')`; dev is every-package-external as before 10-13. Verified: dev 200 on `/` and `/login`, local prod build still carries the 981 KB inlined Sentry chunk, mongodb external.

### Visitor counting (GoatCounter, 2026-10-14)
`src/components/GoatCounter.astro`, mounted in the `<head>` of `KioskLayout` (with `isAdmin`), `LandingLayout` and `AuthLayout` — never `AdminLayout`. It renders only when `GOATCOUNTER_ENDPOINT` is set AND `process.env.VERCEL_ENV === 'production'` AND the session is not an admin (the owner's own visits would be the biggest single visitor). Because the page-load listener outlives a soft navigation from a public page (legal pages, auth door, 404) into a member page, `KioskLayout` (admin session) and `AdminLayout` (always) also emit `<meta name="mh-nocount">` and `send()` returns early when the current document carries it; an admin's view of a public page itself is still counted (accepted). Both env reads compile to run-time `process.env` lookups — a local prod test needs both vars on the SERVER command, not only on the build. Hosted free tier (non-commercial) in the owner's existing GoatCounter account; the portfolio site ercan-atak.de uses the same setup and its CLAUDE.md „Analytics" holds the gotchas (a custom stats domain is vanity only, ad blockers still block `count.js`, so every number is an undercount). Mechanics: `count.js` loads async with `no_onload`, ONE `astro:page-load` listener counts every page (the ClientRouter keeps the document, a window flag registers the listener once; when `count.js` is not loaded yet the listener leaves a `pending` flag and the script's `load` event sends). **Privacy shape (owner decision 2026-10-14):** path only, `/nachbarn/<handle>` collapsed to `/nachbarn/*`, no title, an EXTERNAL referrer with the first view only (document.referrer never changes during a ClientRouter session, and a same-site referrer would carry the previous page's query string — the Opus review caught that `location.href='/login'` after a reset made the first view report `…/reset-password?token=…`), and `goatcounter.get_data` is WRAPPED to blank `q` (flag on the FUNCTION, count.js re-running assigns a fresh one) — count.js sends `location.search` as its own field whatever path you pass, and four pages carry single-use tokens there (`verify-email`, `reset-password`, `confirm-email-change`, `widerrufen`), `/search` the query, `/login` the redirect target. `vercel.json` sends `Referrer-Policy: strict-origin-when-cross-origin` on every response since the same day (the beacon and Cloudinary see the origin only; verify after a deploy with `curl -sI https://mahalle.digital/ | grep -i referrer`). Datenschutz: section 2 „Besucherzählung" (DRAFT copy) + section 4 names the processor — facts from goatcounter.com/help/privacy + /help/sessions (2026-10-14): NO daily salt (the portfolio's DSE says so, wrongly) — session key = site + User-Agent + IP kept IN MEMORY for 8 h, never on disk; stored per view: path, referrer, browser, OS, screen width, location from the IP, language; servers Hetzner Online GmbH, Germany + Finland; operator Martin Tournoij, Ireland; the privacy page mentions no DPA. Probe: `scratchpad/goatcounter/gc-probe.cjs` — 23 checks against the local prod build on :4655 (serves the real `count.js` from the folder in place of gc.zgo.at, forces `allow_local`, records every beacon; the logged-out pages, a soft navigation, the token/redirect/search URLs, an external vs a same-site referrer, a member on `/nachbarn/<handle>`, the admin without a script and with the marker; start the SERVER with `VERCEL_ENV=production GOATCOUNTER_ENDPOINT=…` or nothing renders). LIVE since 2026-10-14 02:16 (`46bf3900`, env redeploy `7aaafd0e`): site code `mahalle` in the owner's GoatCounter account, Data collection = Sessions, Referrer, User-Agent, Size, Country, Region for `DE` only (Bundesland), Language ON, Individual pageviews OFF; dashboard private; no custom domain. A public visitor count on the site (GoatCounter's `/counter/TOTAL.json`, like the portfolio footer) and a public dashboard are ideas for the essay's later parts, not built. DEFERRED (owner, 2026-10-14): a three-number card (today / week / month + dashboard link) beside `AdmErrorsCard` on `/admin/moderation`, same proxy shape (admin gate, read-only API token in env, 60 s cache) — decide after a few weeks of real use; never a chart copy of the dashboard.

### First database connect on a cold instance: one retry, never a Sentry filter (2026-09-20)
`connectDB()` wraps `getClientPromise()` in `connectWithRetry()` (`src/lib/mongoRetry.ts`, pure, tested): a `MongoServerSelectionError` / `MongoNetworkError` / `MongoNetworkTimeoutError` from the INITIAL connect is retried once — the failed attempt is already un-cached and closed, so the second call builds a fresh client. Reason: Sentry MAHALLE-PROD-2 reopened with exactly one event in the minute after a deploy, three times in two days; every stack was `MongoClient.connect → … → Topology.selectServer` (cold start, no pool), and the very next request always succeeded. Deliberately NOT filtered out of Sentry: a real outage has the same signature and must stay loud — it still throws (last error, two attempts ≈ 20 s instead of 10 s) and the middleware captures it. Verified with the real driver (`scratchpad/mongo-retry-live.mts`: unreachable host → dev DB, failed client closed, 0 unhandled rejections; full outage → error after 2 attempts). **The default export `clientPromise` is taken ONCE at module load and never replaced** — if that first connect fails it stays rejected for the life of the instance (the un-cache only frees the globalThis slot), so every `await clientPromise` there keeps failing while `connectDB()` recovers. Since 2026-09-22 (Sentry: the three post-fix blips were all `GET /api/profile/tour`, which awaited it) login (`authorize`), the JWT recheck, `register`, `users/update` and `profile/tour` use `connectDB()`; the Auth.js adapter is the only remaining consumer and is never called with Credentials + JWT. New code: always `connectDB()`, never the default export. Full history: `docs/runbooks/mongo-region-incident.md`.

### Uploads vs Vercel's 4.5 MB body cap (2026-10-25, `16b047e5`)
Raw phone photos (3–8 MB) died at Vercel's edge with a 413 before any function ran, so nothing reached Sentry — a member could not add photos to a marketplace listing. Every picker now calls `shrinkForUpload()` (`src/lib/images/shrinkImage.ts`, browser-only; decisions in the pure, tested `shrinkRules.ts`): long edge 1600 px (avatar 1024), JPEG q0.85, a ladder down to ≤ 4 MB, EXIF orientation honoured, the original file is sent when decoding fails. All image routes (`posts`, `news`, `listings` upload, avatar via `AVATAR_MAX_BYTES`) cap at the shared `UPLOAD_MAX_BYTES` (4 MB). A NEW upload path MUST run its file through the helper first and refuse with `compose.error.imageTooLarge` when it is still too large. Gate: `scratchpad/upload-shrink/probe.cjs` (17 checks on the local prod build: an 11.6 MB photo on all four paths arrives as ~1 MB, a 7 MB EXIF-6 photo is stored upright, a small jpeg passes untouched, a transparent PNG becomes a jpeg, an undecodable 5 MB file shows the „zu groß" sentence on publish AND draft-save without a request, raw 4.2 MB bodies get 400 from all three routes; fixtures from `make.mjs`). Probe lessons: Cloudinary's route transformation (`crop: limit` 1200×800) changes the STORED width/height, so assert on orientation/ratio, not on the uploaded pixel size; CDP omits the bytes of a file-backed `File` in multipart post data (only in-memory blobs are measured) — prove pass-through by the stored result, not the body length. Not verified here: EXIF rotation on a real iPhone portrait photo.
